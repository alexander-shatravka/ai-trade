# 08 — Конвенції розробки

Мета конвенцій — прибрати суперечки на code review. Якщо правило тут є, воно не обговорюється
в PR; якщо його немає — додаємо його сюди, а не сперечаємось удруге.

---

## 1. TypeScript

**`strict: true` завжди.** Плюс:

```jsonc
{
  "strict": true,
  "noUncheckedIndexedAccess": true,   // arr[0] має тип T | undefined — це правда
  "noImplicitOverride": true,
  "exactOptionalPropertyTypes": true,
  "verbatimModuleSyntax": true
}
```

**`any` заборонений.** Якщо тип справді невідомий — `unknown` + звуження через Zod.
Єдиний виняток — інтеграція зі сторонньою бібліотекою без типів, і тоді поруч коментар `// TODO: типи для X`.

**Не використовуємо `as` для приховування помилок типізації.** `as const` і звуження після
перевірки — нормально. `as SomeType` для того, щоб компілятор замовк — ні.

**Валідація на межі системи.** Усе, що приходить ззовні (HTTP-тіло, вебхук, відповідь LLM,
рядок Excel), проходить через Zod-схему з `packages/contracts`. Усередині системи тип уже гарантований.

## 3. Структура модуля NestJS

```
modules/listings/
├── listings.module.ts
├── listings.controller.ts      тонкий: валідація + виклик сервісу, без логіки
├── listings.service.ts         бізнес-логіка
├── listings.repository.ts      усі запити до Prisma
├── dto/                        Zod-схеми реекспортуються з packages/contracts
├── guards/                     ownership, entitlements
└── listings.service.spec.ts
```

**Контролер не звертається до Prisma напряму.** Сервіс не пише сирий SQL повз репозиторій.
Це не догма заради шарів — це те, що дозволяє тестувати логіку без БД.

---

## 4. Робота з БД

- Усі запити — через Prisma. Сирий SQL допустимий лише в пошуку та агрегаціях,
  і тільки через `Prisma.sql` з параметрами (ніякої конкатенації рядків).
- **Кожен новий фільтр або сортування вимагає індексу.** Додав `WHERE` по новому полю —
  перевір, чи є індекс, і додай у тому ж PR.
- Транзакції — для будь-якої операції, що змінює більше однієї таблиці
  (публікація оголошення = `Listing` + `Media` + лічильники).
- Уникаємо N+1: `include` замість циклу з запитами. Це перевіряється на review.
- Міграції ніколи не редагуються після мержу в `main` — тільки нова міграція зверху.

---

## 5. Робота з AI

Правила з [`AGENTS.md`](../AGENTS.md) розділ 5 — обов'язкові. Додатково:

- Кожен AI-виклик іде через `MeteredProvider`, щоб з'явився запис `AiJob`.
- Кожен промпт має версію (`vision.recognize@v4`) і живе в `modules/ai/prompts/`,
  а не інлайном у сервісі.
- Вивід LLM **завжди** валідується JSON-схемою. Невалідний вивід = помилка задачі,
  а не «спробуємо розпарсити як вийде».
- Зміна промпту без прогону `pnpm ai:eval` не мержиться.
- Текст від AI ніколи не рендериться як HTML. Тільки як текст.

## 6. Фронтенд

- **Server Components за замовчуванням.** `'use client'` — лише там, де є стан, ефекти
  або обробники подій. Кожен `'use client'` має бути обґрунтований.
- Дані для SEO-сторінок (каталог, картка товару) тягнуться на сервері. Ніякого
  «спіннер, потім fetch на клієнті» для контенту, який має індексуватися.
- Стан сервера — TanStack Query. Стан UI — `useState`/`useReducer`.
  Глобальний стор заводимо тільки коли з'явиться реальна потреба, не заздалегідь.
- Форми — `react-hook-form` + `zodResolver` зі схемою з `packages/contracts`.
- Стилі — Tailwind з токенами дизайн-системи. Довільні значення (`w-[437px]`) —
  ознака того, що щось не так із сіткою; допустимі лише як виняток із коментарем.
- Кожен інтерактивний елемент має видимий фокус. `outline: none` без заміни — блокер на review.
- Перевірка в темній темі обов'язкова перед відкриттям PR.

## 7. Помилки

**Бекенд:** RFC 9457 `application/problem+json`. Кожна помилка має стабільний `type`-URI,
за яким фронтенд приймає рішення — не парсимо текст повідомлення.

```ts
throw new AppError({
  type: 'limit-exceeded',
  title: 'Вичерпано ліміт AI-створень',
  status: 403,
  detail: `Тариф ${plan.name} дозволяє ${limit} створень на місяць.`,
  upgradeUrl: '/pricing?from=ai-limit',
});
```

**Ніколи не ковтаємо помилки мовчки.** `catch {}` без логування або обробки — блокер.
Якщо помилка очікувана й нецікава — коментар, чому саме її ігноруємо.

**Фронтенд:** error boundary на кожному маршруті. Користувач бачить, що пішло не так,
і що з цим робити — не «Something went wrong».

## 8. Тести

| Рівень | Чим | Що покриваємо |
|---|---|---|
| Unit | Vitest | Бізнес-логіка сервісів, `packages/utils`, парсери |
| Integration | Vitest + Testcontainers (Postgres) | Репозиторії, складні запити, транзакції |
| Contract | Zod-схеми + приклади з OpenAPI | Що API віддає те, що обіцяє |
| E2E | Playwright | Критичні флоу з `AI_PROVIDER=mock` |
| AI eval | `pnpm ai:eval` | Якість промптів на 200 розмічених кейсах |

**Обов'язково покриті e2e:** реєстрація → верифікація телефону → AI-флоу → публікація;
пошук → картка товару → чат; оплата підписки; масовий імпорт.

Тести AI-флоу працюють на `MockProvider` — детерміновано, безкоштовно, без залежності
від доступності зовнішнього API. Тест не має падати через те, що модель сьогодні
написала інший заголовок.

Не ганяємось за відсотком покриття. Ганяємось за тим, щоб критичні шляхи мали тест,
який реально ловить регресію.

## 9. Git

**Гілки:** `main` (захищена) ← `feat/ai-price-suggestion`, `fix/exif-strip`, `chore/deps`.

**Коміти — Conventional Commits, англійською:**

```
feat(ai): add three price scenarios instead of a single price
fix(media): strip EXIF before uploading to S3
refactor(listings): extract queries into a repository
docs(api): update openapi.yaml after the /search change
chore(deps): bump Prisma to 6.4
```

Типи: `feat` `fix` `refactor` `perf` `docs` `test` `chore` `style`.

**PR:**
- Один PR — одна логічна зміна. 400+ рядків диффу — привід розбити.
- Опис відповідає на три питання: що змінилось, навіщо, як перевірити.
- Скриншот або запис для будь-якої зміни UI — обидві теми.
- CI зелений: lint → typecheck → test → e2e.
- Зміна контракту API → `openapi.yaml` у тому ж PR. Це перевіряється.

## 10. Code review — на що дивимось

Питання, які варто ставити, у порядку важливості:

1. **Гроші не float?** Суфікс `Kop` на місці?
2. **AI не називає число, яке можна порахувати SQL?**
3. **Що станеться, коли AI недоступний?** Є деградація або чесне повідомлення?
4. **Ліміт перевіряється до виклику, списується після успіху?**
5. **Новий фільтр має індекс?**
6. **Дані ззовні провалідовані Zod на межі?**
7. **Помилка не проковтнута мовчки?**
8. **Фокус видимий, темна тема перевірена?**
9. **Контракт синхронізований між `openapi.yaml`, `packages/contracts` і реалізацією?**
10. Читабельність: чи зрозуміє це людина, яка прийде через пів року.

Чого **не** робимо на review: суперечок про форматування (це робота Prettier),
переписування чужого коду в своєму стилі, блокування PR через дрібниці без пояснення.
